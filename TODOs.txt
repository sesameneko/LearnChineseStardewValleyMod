M2 segmentation data — every *imported* table is authored; five families were never imported
--------------------------------------------------------------------------------------------
All 9,039 entries across every Strings/* table and the nine Content/Data
assets in segtool.py's DATA_TABLES have hand-authored segment data; 11 keys are
deliberately skipped (event command scripts, which the game never draws as a
single string). `segtool.py status` shows pending=0 everywhere and
`segtool.py validate` passes.

That is NOT the same as "all game text" — a distinction this file previously
got wrong. Found 2026-09-22, when villager dialogue turned up untranslated in
play: five asset families were never in scope at all, ~8,900 drawn pages /
~291k JA characters, roughly 1.5x everything authored to date (199,699).

  Characters/Dialogue/*   52 files   3,301 keys   4,874 pages   161,892 chars
  Data/Events/*           44 files   2,064 spoken lines in 258 scripts   80,793
  Data/Festivals/*         9 files     743 keys   1,025 pages    30,996
  Data/TV/*                2 files      96 keys                  10,827
  Strings/schedules/*     30 files     191 keys                   6,139

Update 2026-09-23: all five are now extracted (tools/extracted-strings/content-ja,
content-en) and wired into segtool.py as <Family>-<file> tables, so `status` counts
them. That makes 6,519 entries (~301k chars) pending. The flat ones (dialogue,
schedules, festivals, TV) are also in TranslationIndex.StringTables for
whole-sentence lookup.

Run `segtool.py audit` for the live version of that list. It walks the game's
Content folder and fails on any localized asset the pipeline can't account for,
which is the check that was missing — `status` only ever measured coverage
against the files somebody had already chosen to extract. See Plan.md's data
task for the full post-mortem.

Still open beyond those five: Achievements / SecretNotes, which
tools/XnbStringTool still can't read (Dictionary<int,string>), and the
TranslationIndex.StringTables array in the mod itself, which has the same
Strings/*-only blind spot for whole-sentence lookup.

The pipeline, for future re-passes (tools/segment-data/segtool.py):

  python3 tools/segment-data/segtool.py status          # coverage per table
  python3 tools/segment-data/segtool.py batch Tools 50  # next worklist, as TSV
  ...author a .tsv...
  python3 tools/segment-data/segtool.py merge Tools batch.tsv
  python3 tools/segment-data/segtool.py validate

Authoring format is one entry per line, tab-separated:
  key <TAB> english <TAB> text¦reading¦gloss‖text¦reading¦gloss‖...
merge rejects any line whose segment texts don't concatenate back to the
source string exactly, so bad data can't reach the mod.

Output goes to tools/extracted-strings/literal-translations/<Table>.json —
that folder is the tracked source of truth; assets/segments/ is gitignored and
generated from it by the csproj's CopySegmentData target.

Status: all imported tables complete (9,039 authored, 11 skipped, 0 pending);
five un-imported families outstanding, see above.
